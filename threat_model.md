# Threat Model

## Project Overview

Academy Toolkit is a production web application for private video-marketing practice and related email/video marketing tools. It uses a React 18/Vite frontend, a Node.js/Express TypeScript backend, PostgreSQL with Drizzle ORM, Express sessions stored in PostgreSQL, local/object video storage, Google Gemini/OpenAI integrations, Google OAuth, SendGrid inbound email parsing, YouTube/yt-dlp processing, and ClickFunnels enrollment/SSO integration.

The product and repo documentation describe the Toolkit as an active-member service tied to ClickFunnels enrollment. That membership boundary is therefore in scope for production security review: signup, login, session checks, revocation handling, and downstream SSO should all enforce the intended member-only access model rather than treating enrollment as display-only metadata.

Production scope is the Express API in `server/`, shared schema/types in `shared/`, and the built React client in `client/`. Development-only Vite middleware, Replit cartographer/runtime-error tooling, node_modules, attached assets, and mockup/sandbox artifacts are out of scope unless reachable when `NODE_ENV=production`.

## Assets

- **User accounts and sessions** -- email/password accounts, Google OAuth identities, PostgreSQL-backed session IDs, admin/super-admin roles, disabled-user state, and ClickFunnels enrollment status. Compromise allows impersonation and access to private practice data.
- **Private video practice data** -- uploaded videos, converted/HLS previews, thumbnails, transcripts, AI scores, generated PDFs, folder organization, and processing metadata. These are private to the user unless an admin is explicitly viewing them.
- **Email analyzer data** -- unique inbound seed addresses, received email bodies/HTML/headers, authentication analysis, sender IPs/domains, AI copy feedback, scores, and admin-managed seed inbox Gmail OAuth tokens.
- **Marketing research and content data** -- Topic Pulse runs, generated topics, saved topics, generated scripts, link placeholders, saved offers, and Keywords Everywhere API keys.
- **Application secrets and external credentials** -- `SESSION_SECRET`, database URL, OpenAI/Gemini integration keys, Google OAuth secrets, SMTP credentials, ClickFunnels API/webhook secrets, SendGrid inbound trust assumptions, and encrypted user API keys.
- **Admin data and audit logs** -- user lists, admin session views, account merge/disable actions, ClickFunnels access controls, app settings, aggregate credits, and action logs.

## Trust Boundaries

- **Browser to Express API** -- all `/api/*` requests cross from an untrusted client to trusted server logic. The server must authenticate and authorize every private resource; client-side route hiding is not a control.
- **Public/authenticated/admin boundary** -- login, signup, password reset, OAuth, ClickFunnels login, SendGrid inbound parse, and static assets are public; most app data routes require a valid session; admin routes require server-side admin checks. Member-only ClickFunnels enrollment is a separate boundary from ordinary authentication and must be enforced where the product promises members-only access.
- **Express to PostgreSQL** -- API input is persisted and queried via Drizzle. SQL must remain parameterized, and every lookup/update/delete of user-owned records must be scoped to the authenticated user unless guarded by admin checks.
- **Express to filesystem/object storage** -- uploaded or externally downloaded videos, generated thumbnails/posters/HLS segments, transcripts, and PDFs cross into storage and ffmpeg/yt-dlp processing. Paths must be generated by the server, constrained to intended storage roots, and authorized before serving.
- **Express to external services** -- Gemini/OpenAI, Google OAuth, ClickFunnels API/webhooks/SSO, SMTP, SendGrid inbound parse, YouTube/yt-dlp, Keywords Everywhere, and DNS blacklist checks are external trust boundaries. Requests should validate source/signatures where applicable and avoid user-controlled SSRF or unsafe redirects.
- **Email/webhook boundary** -- SendGrid inbound payloads and ClickFunnels webhooks are unauthenticated network inputs unless verified by a shared secret/signature or by unguessable mailbox tokens.
- **Admin/user boundary** -- admin actions can view or alter user accounts and sessions; those routes must require server-side role checks, record audit evidence, and prevent non-admin escalation. Seed inbox configuration and Gmail mailbox binding belong to this boundary even when the resulting inbox list is later used by non-admin features.

## Scan Anchors

- Production entry points: `server/index.ts`, `server/routes.ts`, `server/static.ts`, `server/storage.ts`, `shared/schema.ts`.
- Auth/session/high-risk routes: `/api/auth/*`, `/api/auth/cf-login`, Google OAuth routes, `requireAuth`, `requireAdmin`, session setup in `server/routes.ts`, and user/session storage methods in `server/storage.ts`.
- Private data surfaces: `/api/sessions*`, upload/confirm/download routes, local `uploads/`, object storage integration under `server/replit_integrations/object_storage/`, `server/processing.ts`, `server/ffmpeg.ts`, and `server/youtube.ts`.
- Admin and integration surfaces: `/api/admin/*`, `/api/webhooks/clickfunnels`, `/api/clickfunnels/sso-url`, `server/clickfunnels.ts`, and audit logging in `server/userActionLog.ts`.
- Email analyzer surface: `/api/inbox-analyzer/*`, SendGrid inbound route, `server/inboxAnalyzer.ts`, `server/gmailOAuth.ts`, and placement-monitoring logic in `server/placementScheduler.ts`.
- Topic Pulse/API-key surface: `/api/topic-pulse/*`, `/api/youtube/*`, `server/topic-pulse.ts`, `server/youtube.ts`, and API-key encryption helpers in `server/storage.ts`.
- Request parsing and failure handling: global body parsers and top-level error middleware in `server/index.ts`, especially any code that buffers public request bodies or rethrows request errors.
- Dev-only/out-of-scope: Vite dev middleware in `server/vite.ts`, Replit development plugins, `.local/state`, workflow logs, `attached_assets`, `node_modules`, and generated `dist` content except static serving configuration.

## Threat Categories

### Spoofing

The app has multiple login mechanisms: password login, Google OAuth, ClickFunnels one-click login, and session cookies. Every route that creates or changes a session must prove the caller controls the identity being logged in. Login and account-connection flows should reject cross-site session planting with Origin or CSRF defenses, and successful authentication should rotate the session identifier instead of reusing a pre-login anonymous session. Session cookies must be signed with a strong production-only secret, stored server-side, `HttpOnly`, `Secure` in production, and not accepted for disabled users.

### Tampering

Users can create and modify sessions, folders, DMO entries, scripts, saved topics/offers, API keys, inbound-email records, and account profile fields. Server-side validation must enforce allowed fields, ownership, and business rules. Admin-only mutations such as disabling users, granting ClickFunnels access, merging accounts, and changing credit limits must require `requireAdmin` and should be audit logged.

### Information Disclosure

Video recordings, transcripts, email bodies, generated scripts, user API keys, user lists, and admin views are sensitive. API responses and file-serving routes must scope records to `req.session.userId` unless explicitly admin-authorized. Shared admin-managed inboxes must not become query or presence oracles for ordinary users. Logs must not expose secrets, password reset tokens, raw user API keys, or large private content. Error responses in production must not disclose stack traces or internal storage details.

### Denial of Service

The app accepts large video uploads, runs ffmpeg/yt-dlp, makes AI calls, performs DNS blacklist checks, and processes inbound emails. Public and authenticated endpoints that trigger expensive work need size limits, format validation, per-user/IP rate limits or quotas, timeouts, and safe concurrency controls. Session middleware should not create durable anonymous server-side state on every request unless the route truly needs it, and public request handlers should avoid unbounded body buffering. Error handling must fail the request without crashing the process.

### Elevation of Privilege

Access control must be enforced after authentication for every user-owned object: session IDs, folder IDs, topic runs/topics/scripts/saved topics/offers, API keys, DMO entries, email analyses, and generated file paths. Admin status must be checked from trusted server-side state for each admin route. Integration shortcuts must not allow a user or anonymous caller to impersonate another account by supplying an email, user ID, session ID, object path, redirect target, or token.

### Injection and Unsafe Processing

Database access should use parameterized Drizzle APIs or safe tagged SQL. User-controlled filenames, object paths, YouTube URLs, email HTML, generated script content, and AI output must not be passed into shell commands, filesystem paths, HTML sinks, redirects, or SQL without validation/encoding. Child-process calls to ffmpeg and yt-dlp should use argument arrays and server-generated paths. User-supplied URLs should be constrained to expected hosts when downloaded server-side.
