PART 3: Most Likely Root Causes (You Must Check All)

Because it breaks after logout/login and results in 500, focus on these:

A) Storage key resolution depends on session cookie state

After login, code path might resolve the wrong userId or wrong environment storage path.
Fix:

Never derive storage key from cookie-only state.

Always derive previewVideoStorageKey from the session record in DB by sessionId.

Ensure ownership check happens separately and does not mutate the key.

B) Video endpoint is trying to serve a signed URL that is expired or not regenerated

If you store signed URLs in DB, they will expire and fail later.
Fix:

Store only storageKey in DB.

Generate a fresh signed URL per request, never persist signed URLs.

C) Pathing differences between “dev” and “published” environments

After relogin, the app might run in a different environment or different base path.
Fix:

Use absolute, environment-safe paths.

Do not rely on current working directory.

Use a stable storage location, and store full storage keys.

D) Range request handling bug

The endpoint might crash when Range header exists.

After relogin, the browser may request Range differently.
Fix:

Implement robust Range parsing:

Validate range values

Clamp ranges to file size

Return 416 for invalid ranges, not 500

Return 206 with correct Content-Range, Content-Length

E) Auth middleware returns HTML redirect, and streaming code breaks parsing

If middleware returns HTML, player might show errors, but your code might throw and cause 500.
Fix:

For /api/video endpoints, auth failures must return 401 JSON, never redirect.

F) File is being deleted or moved after processing

A cleanup task might be deleting preview files too early.
Fix:

Verify expiresAt logic.

Ensure no job deletes preview before 30 days.

Ensure “delete original upload” does not accidentally delete preview.

G) Cache layer serving wrong response

If you introduced caching headers incorrectly, you could be caching a 500 or a signed URL.
Fix:

For authenticated streaming endpoints, set:

Cache-Control: no-store

For signed URL playback, signed URL itself can be cached client-side briefly, but do not cache the API response for long.

PART 4: Required Durable Playback Architecture (Implement This If Not Already)

To make this bulletproof, implement the following:

A) Store persistent keys, not URLs
Sessions table must store:

previewVideoStorageKey (persistent, never changes)

previewPosterStorageKey (persistent)

expiresAt (30 day expiration)

Never store:

signed playback URLs

filesystem absolute paths that can change between deployments

B) Playback endpoint must derive the file from DB every time
GET /api/sessions/:id/video/preview/stream
Steps:

Authenticate user

Authorize ownership/admin

Load session record by :id

Resolve previewVideoStorageKey

Map storage key to a real file location or object storage

Stream the file with Range support

Return correct headers

If previewVideoStorageKey is missing:

return 404 with JSON: { error: "Preview not ready" }

C) Signed URL approach (alternative)
GET /api/sessions/:id/video/preview/url

Generate a fresh signed URL each time

Return it to client

Client sets video src to signed URL
Do not save the signed URL in DB.
