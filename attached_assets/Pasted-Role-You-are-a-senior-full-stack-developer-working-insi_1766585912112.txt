PART A: Video Processing Progress Bar

Goal
Users need a clear progress bar and status text for the full processing pipeline after they finish a recording or upload.

Define “processing”
Processing includes the steps that happen after a video is captured:

Upload complete

Transcode to MP4 1080p (if not already)

Compression pass (balanced quality and file size)

Transcription

Scoring (5-part formula)

Recommendations generation

Report ready

Required UX

On the Dashboard and on the Session page, each new session must show:

A progress bar (0 to 100)

A status label (example: “Transcribing”)

A step indicator (example: “Step 4 of 7”)

A last updated timestamp

Progress must update automatically while the user stays on the page.

If the user refreshes or logs out and logs back in:

The progress state must persist and resume, based on server data.

If processing fails:

Show a clear error state and allow a retry action where possible (example: retry transcription).

When processing finishes:

Progress goes to 100%

The session automatically transitions to the results view (video player, scoring, transcript, recommendations).

Backend architecture
Use one of these reliable patterns, whichever matches the existing stack:
Option 1 (preferred): Server Sent Events (SSE)

Client subscribes to /api/sessions/:id/progress/stream

Server pushes updates when status changes
Option 2: WebSockets

Use an existing WS setup if already present
Option 3: Polling (fallback)

Client polls /api/sessions/:id/progress every 2 seconds until complete

Database changes
Add processing fields to the Sessions table:

processingStatus (string, enum-like)
Values:
queued, uploading, transcoding, compressing, transcribing, scoring, recommending, ready, failed

processingStep (integer 1-7)

processingProgress (integer 0-100)

processingMessage (string, short human label)

processingError (text nullable)

processingStartedAt (datetime nullable)

processingUpdatedAt (datetime nullable)

processingCompletedAt (datetime nullable)

Also add a ProcessEvents table for better debug (recommended):
ProcessEvents

id

sessionId

status

progress

message

createdAt
This helps reliability and admin support.

Server processing flow requirements

When a session is created:

Create DB row immediately with status queued and progress 0.

Start processing pipeline in a background job:

Do not block the HTTP request.

After each step:

Update sessions table fields

Insert a ProcessEvents row

Emit progress updates through SSE/WS if enabled

Handle retries:

If a step fails, store error and mark failed.

Allow retry for steps that can be retried (transcription, scoring, recommendations).

Retrying should not create a new session unless explicitly requested.

Acceptance checks for progress

Progress increases in real time

Status labels match actual pipeline state

Refreshing the page shows accurate current progress

When done, the UI shows full results automatically

PART B: Interactive Transcript Editor With Highlighting and Playback Sync

Goal
Users can edit the transcript, see text highlighted as the video plays, and click transcript text to jump the video to that moment.

Key requirement
To sync transcript to playback, you must store timestamps for transcript segments or words.

Transcript data model
Store transcript as structured segments with timestamps:
TranscriptSegments

id

sessionId

startMs (integer)

endMs (integer)

text (string)

confidence (optional)

createdAt

updatedAt

Do not rely on a single blob of text if we need sync and editing.
If you already have transcript text stored, migrate it into segments after next transcription.

Transcription output requirements
Ensure transcription produces at least segment-level timestamps.

Segment-level is acceptable.

Word-level is a bonus if it is easy and stable.
If using Whisper or similar, enable timestamped segments.

Transcript editor UX
On the Session results page, add a Transcript panel with:

Playback synced highlighting

As video plays, the current segment is highlighted.

Past segments can have a subtle style difference.

Click to seek

Clicking a segment seeks the video to that segment start time.

Inline editing

User can click a segment and edit its text.

Provide Save and Cancel controls.

Auto-save is optional, but must be safe.

Search inside transcript

A search input that highlights matches and jumps to next match.

“Reset transcript to original” option

Restores the transcript to last generated version if the user wants.

“Regenerate transcript” still exists if you already have it.

But it should regenerate the segments too.

Playback sync implementation

Add a timeupdate listener on the video element (4 to 8 times per second max).

Determine current segment by currentTimeMs and segment start/end.

Efficient lookup:

Use binary search on segment start times instead of scanning 900 segments each tick.

Scroll behavior:

Auto-scroll the transcript panel to keep the current segment visible.

Do not fight user scrolling. Add a toggle like “Follow playback” on by default.

Saving edits
Implement endpoint:
PATCH /api/sessions/:id/transcript
Body:
{
"segments": [
{ "id": "...", "text": "..." }
]
}
Rules:

Only owner of session (or admin) can edit.

Validate max length per segment.

Store updatedAt timestamps.

Keep a copy of original transcript:
Either:

transcriptVersioning table, or

store original JSON snapshot in sessions.transcriptOriginalJson

Export implications
When user edits transcript, use the edited transcript for:

PDF report generation

Any user facing display
Do not silently overwrite original without keeping a backup.
